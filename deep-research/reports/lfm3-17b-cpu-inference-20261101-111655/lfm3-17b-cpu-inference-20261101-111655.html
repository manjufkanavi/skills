The Model: Tri-Hybrid Architecture

  • 24 layers = 13 gated short-conv (kernel 7) + 5 sliding-window attn (256 tok) + 6 global attn
  • GQA 4:1 · head dim 128 · partial RoPE · QK-norm · sandwich norm · 128K vocab · 256K context
  • Pre-trained on 22T tokens; ~1 GB at 4-bit
  • Why it matters: 13/24 layers are cheap convs → decode is memory-bandwidth-bound, not compute-bound

Quant Selection (evidence-based)

  • arXiv unified eval (2601.14277): Q4_K_M/Q4_K_S = non-dominated accuracy–compression frontier; Q3 and below = disqualifying accuracy loss
  • Decode is bandwidth-bound → decode t/s scales ~linearly with weight size (Q8_0 ≈ 1.7× Q4 traffic)
  • Prefill is compute-bound → quant choice affects prompt processing far less
  • 31 GiB RAM removes the usual Q4 constraint → benchmark the full ladder

CPU Tuning — i7-6700K (Skylake)

  • 4 physical / 8 SMT threads · AVX2, no AVX-512 · DDR4 dual-channel ≈ 26 GB/s peak
  • Decode ceiling: Q8_0 ≈ 26 GB/s ÷ 1.85 GB ≈ ~14 t/s theoretical
  • llama.cpp (Oct 2026): auto threads now prefer physical cores — memory-bound workloads suffer with SMT siblings sharing the controller
  • KV cache f16 at 64K ctx ≈ 1.5 GB → KV quant / flash-attn buy nothing at this model size; keep defaults

Benchmark Methodology

  • Raw engine: llama-bench b12024, -ngl 0, -p 32768,65536 -n 128,256 -r 3 per quant → pp/tg t/s
  • Serving layer: llama-server -c 66560 (OpenAI-compatible, same surface LocalAI exposes) → streamed /v1/completions with exact-token 32K/64K real-text prompts → TTFT + output TPS
  • SMT probe: t=4 vs t=8 on anchor quants

Key Takeaways

  • llama.cpp v0.8.0+ is the only mainstream engine with native LFM3 GGUF support
  • Q8_0 for quality, Q4_K_M for speed — RAM allows both; the 6700K allows ~10–30 t/s class decode
  • Physical-core threads (4) for decode; SMT (8) may win prefill — measured, not assumed
  • Base model = raw continuation; ship LFM3-1.7B (instruct) for products
  • 64K context costs ~1.5 GB KV — the 256K-capable model runs comfortably on a 2015 desktop CPU
