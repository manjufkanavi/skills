# LFM3-1.7B on Bare CPU: Quantization & Inference Engine Research

**Question:** What is the correct model quant and inference engine for
`LiquidAI/LFM3-1.7B-Base` on a bare-CPU Linux box (i7-6700K, 8 threads, 31 GiB RAM, no discrete GPU)?

## 1. Definition

LFM3-1.7B-Base is Liquid AI's 1.73B-parameter **pre-trained** text checkpoint built on the new
**tri-hybrid** architecture: of its 24 layers, 13 are gated short convolutions (kernel size 7),
5 are sliding-window attention (256-token window) and 6 are global attention. It was trained on
22T tokens, has a 256K-token context window, 128K vocabulary, GQA 4:1 (16 query / 4 KV heads,
head dim 128), partial RoPE, QK-norm and sandwich norm. At 4-bit precision it takes ~1 GB of
memory. The Base checkpoint is intended for continued pre-training/post-training; the chat model
is `LFM3-1.7B`.

## 2. Why it emerged

Liquid's LFM2 hybrid (conv + attention) proved fast on device; LFM3 adds a third operator (SWA
inserted between conv and global attention), a larger conv kernel, and head-wise gating, then
extends context to 256K via mid-training. The payoff: per-parameter, LFM3-1.7B matches LFM2-1.2B
on short prompts and is ~25% faster at 8K context — because 13 of 24 layers are cheap convs,
**decode is memory-bandwidth-bound, not compute-bound** (conv cache L=7 is tiny). That single
property dictates everything about CPU deployment: pick an engine that streams weights and KV
cache through DDR4 efficiently.

## 3. Mechanics — the engine landscape

| Engine | LFM3 support | CPU suitability | Verdict |
|---|---|---|---|
| **llama.cpp** (GGUF) | ✅ native `lfm3` arch, PR #31252 merged 2026-10-27, shipped in **v0.8.0 (b11960)** | Purpose-built, AVX2, K-quants, KV management, llama-server OpenAI API | **CHOSEN** |
| LocalAI (mudler) | wraps a llama.cpp backend image (on-demand pull) | Go orchestrator + backend; multi-model, OpenAI-compatible | Valid for serving; the engine underneath is still llama.cpp |
| vLLM / SGLang | ✅ (CPU builds exist) | Weak CPU story, NVFP4 path is GPU-only | Rejected for this box |
| MLX | ✅ (4-bit) | Apple Silicon only | N/A (Linux) |
| ExecuTorch | community port | Mobile/edge AOT | Overkill |
| HuggingFace transformers (BF16, remote code) | ✅ | No quant, single-process, ~5-10x slower than llama.cpp on CPU | Rejected for serving |

Key facts: (1) no *official* `LFM3-1.7B-Base-GGUF` exists — the Base GGUF set used here is
`saidutta69/LFM3-1.7B-Base-heretic` (all 15 quants + official safetensors, SHA256-verified,
built with llama.cpp master 2026-10-28); the official GGUF repo exists only for the post-trained
model. (2) llama.cpp v0.8.0 (Oct 28, 2026) is the first release with LFM3 support; anything
older fails to load. (3) llama.cpp's auto thread sizing (`-t -1`) was changed to prefer
**physical cores** (Oct 2026) because inference is memory-bound and SMT siblings share the same
L1/L2/memory controller.

## 4. Quantization selection

Evidence (arXiv 2601.14277, unified llama.cpp quant evaluation on Llama-3.1-8B, Xeon AVX-512):
- **Q4_K_M / Q4_K_S sit on the non-dominated accuracy–compression frontier** with a large
  generation-speed gain vs F16 — the community default for a reason.
- Q3_K_S and below maximize throughput but with accuracy loss "large enough" to be
  disqualifying for quality-sensitive use.
- Q8_0/F16 are the quality ceiling; cost is ~2x the weight bandwidth of Q4 — and decode is
  bandwidth-bound, so decode t/s scales roughly with weight size.
- Prefill (prompt processing) is more compute-bound: quant choice affects it far less than it
  affects decode.

Liquid's own model card states 4-bit is the design point ("~1 GB, fits any phone or laptop"),
and its published edge benchmarks use Q4_0 GGUF in llama.cpp.

**Decision for this box (31 GiB RAM):** benchmark the full ladder — Q2_K, Q4_0, Q4_K_M,
Q5_K_M, Q6_K, Q8_0 — because Q8_0 (1.85 GB) fits trivially in 31 GiB, so the usual RAM
constraint that forces Q4 does not apply. Anchors: **Q8_0** (quality ceiling, expected
lowest decode t/s), **Q4_K_M** (design point, expected highest decode t/s). Expect Q8_0 ≈ 1.7x
the weight traffic of Q4_K_M.

## 5. CPU tuning for i7-6700K

- Skylake: 4 physical / 8 SMT threads, AVX2 (no AVX-512), DDR4 dual-channel (~26 GB/s
  theoretical). Decode bandwidth ceiling for Q8_0 ≈ 26/1.85 ≈ **~14 t/s theoretical max**
  (realistic 6-12 t/s after conv/KV overhead).
- Threads: use **4 (physical)** for decode-heavy work; 8 SMT can help compute-bound prefill.
  llama.cpp b12024 auto mode (-t -1) already picks physical cores.
- KV cache: f16 default. 64K ctx KV for 1.7B (11 attn layers, GQA 4 KV heads, head_dim 128)
  ≈ 1.5 GB — negligible on 31 GiB, so KV quantization (q8_0/TurboQuant) buys nothing here;
  keep f16 for quality. Flash attention on CPU is a memory optimization with mixed speed
  reports — keep default (auto) and rely on measured numbers.
- Batch/ubatch: defaults (b=2048, ub=512) are fine for prefill; context auto-sizes to
  prompt+gen in current llama-bench.

## 6. Benchmark methodology (to be executed)

1. **Raw engine** (`llama-bench`, built from b12024, `-ngl 0`): `-p 32768,65536 -n 128,256
   -r 3` per quant → prompt-processing (pp) and token-generation (tg) t/s, context
   auto-sized.
2. **Serving layer** (`llama-server -c 66560`, OpenAI-compatible — the same surface LocalAI
   exposes): stream `/v1/completions` with exact-token-count 32K/64K real-text prompts
   (official LFM3 tokenizer) → TTFT (= prompt processing wall time) and output TPS.
3. Thread sweep t=4 vs t=8 on the anchor quants to answer the SMT question empirically.

## 7. Risks & caveats

- **Base ≠ instruct**: output is raw continuation (with inherited thinking traces), not
  chat-formatted. Use LFM3-1.7B for products.
- Community GGUF for Base: verified via SHA256 + reproduce metadata; official upstream GGUF is
  instruct-only.
- 6700K is a 2015 part: no AVX-512, single-channel-capable DDR4 if the board populates one DIMM —
  measure actual memory bandwidth; decode t/s is directly proportional to it.
- llama.cpp ≥ v0.8.0 required; older builds silently fail to load lfm3 GGUFs.
