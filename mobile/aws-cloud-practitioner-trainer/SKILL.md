# AWS Cloud Practitioner Trainer — repo map, UX workflow, APK delivery

## When to Use
Any task on the user's CLF-C02 study app: screen redesigns, journey-map or theme changes, rebuilds, or questions about the app's structure. The recurring shape: redesign a screen → update code AND the UX doc → rebuild → commit + push → send the APK on Telegram.

## Bug-list protocol (owner standing rule)
When the owner sends a numbered list of bugs/features: understand the codebase first, then fix **one item at a time** — build → install on the emulator → drive it → send screenshot evidence on Telegram → **stop and wait for the owner's go-ahead** before starting the next item. Never batch several fixes into one build/APK; each item ships with its own evidence. Items that are design choices (owner picks from N options) pause on *presenting* the options, not on implementation. Exception: an explicit owner instruction in the current message (e.g. "build and send me a new apk after all fixes") overrides the one-fix-per-build rule — batch them, ship one APK, one commit, then push.

## Voice reader / TTS (v3.19 → v3.23)

- `theme/Tts.kt` (`TtsEngine`) wraps `TextToSpeech`: reads the concept explanation end-to-end (markdown stripped; the v3.8 `tts_text` companion) and applies the learner's settings before every speak — **gender (Female/Male), accent (India/US/UK/Australia — four accents; S. Africa removed in v3.23.1 because the 2025 catalog has no en-ZA voices), speed 0.5–3×** — persisted in `state/AppState.kt`; owner defaults = **India + Male + 0.8×** (v3.23.1 set gender + accent; v3.24: speed 1×→0.8×) — both the in-memory state initialisers and the fresh-install prefs reads in `state/AppState.kt`. Settings screen renders the gender chips + accent list + "Download voice data".
- **The voice-query worker must actually be `.start()`-ed.** v3.21 shipped a Kotlin `Thread { }` that was never started (the constructor does **not** autostart; `thread{}` does) — it compiles, deploys, produces zero errors, and never runs: gender chips (gated on `knownVoices.isNotEmpty()`) stayed hidden on every device and the reader caption fell back to the stored gender while the engine played its default voice. If a worker's first log line never appears, verify the thread exists in the process thread table before suspecting logging, the framework, or scheduling.
- `voiceQuerySettled` = true only once the query has **definitely** completed (non-empty, or the retry budget exhausted). UI rules: chips render only once settled; "settled with zero voices" shows the download prompt; "not settled" shows loading — never flap between them.
- **Gender is not in the public API** (`Voice` exposes only name/locale/quality/latency/features/network; modern Google voices use opaque codes), and the engine's own signed catalog is the ONLY complete gender source: `KNOWN_VOICE_GENDER` (v3.23) is the 314-voice/81-locale table decoded from Google TTS's `assets/voices-list-dsig.pb` (field 16: 1 = female, 2 = male). **Never re-seed the map from web voice databases** (Readium et al. carry only old-generation `-network` codes → most locales read "unknown" → the first-in-locale fallback plays the engine's default voice, females list first — the whole "label says male, plays female" bug class). Key normalization, anchors, and the decode recipe: `references/tts-voice-gender.md`. Resolution order (v3.23): documented voice of the requested **gender** (wins over accent) → another English reader accent in list order (saves accents the engine no longer ships) → any voice of the locale (gender unknown — caption honestly) → any documented voice of the gender. `applyReaderSettings` then `setVoice`s the resolved voice directly — `setLanguage` only when nothing resolves (v3.22's download gate routed cross-locale picks to `setLanguage` and the engine silently played its default). The `Locale("en","GB","male")` variant trick remains a tested dead end on the 2025 engine.
- **Honest captions** (`voiceDisplayName`): a voice is labelled Male/Female only when its gender is established, and is captioned with its **actual** locale — a cross-locale fallback reads "Male Indian English", never the accent the learner asked for (v3.23). Raw opaque engine codes never surface in learner-facing UI (v3.22 rule — the settings "Voice: …" line uses the display name). Displaying an unverifiable gender or a code IS the "label says male, plays female" bug class — never do it.
- **Download button** (`voiceDownloadTargets`): the manifest must carry a `<queries>` block (package + intents) or Android 11+ `resolveActivity` returns null. Cascade: `INSTALL_TTS_DATA` → legacy `com.google.android.tts.SETTINGS` → `market://details` → Play https → raw `android.settings.TTS_SETTINGS` (no public SDK constant); first resolved wins. On the 2025 engine build `INSTALL_TTS_DATA` is the ONLY exported settings surface → the "Your languages / Available languages" voice-data screen; never land on the Play Store page for an already-installed app.
- **Field triage:** `adb shell am start -n com.example.awsredesign.debug/com.example.awsredesign.MainActivity --ez awt_tts_selftest 1` boots a throwaway engine and logs `TtsSelftest` diagnostics (voice counts, per-gender selection, intent resolution, utterance start/done/error, engine deaths). Add `--ez awt_tts_resolve_all 1` for the fast accent×gender resolution matrix (no slow speaks) — the FIRST check for any voice-gender complaint; run `adb shell pm clear com.example.awsredesign.debug` beforehand to test fresh-install defaults. The `Tts`-tag timing + utterance-trace logs are unconditional in release builds **on purpose** — the only window into a field phone.
- **Emulator caveats (S24 Ultra AVD `S24Ultra_API_36.1`, Android 16):** launch with audio ON (a `-no-audio` instance stalls `getVoices()` >30s); the engine's tflite thread can SIGILL on first synthesis of some models — an emulated-CPU artifact, not an app bug: selection is proven via the engine's per-voice Synthesis log lines, audio playback must be confirmed on a real device. On-device voice facts (2025 build): 473 voices total, all opaque codes; the 2025 signed catalog = 81 locales / 314 voices, English present only in en-AU/en-GB/en-IN/en-NG/en-US, **no en-ZA at all** — a S.-Africa request can never play South African English (it falls back to the closest English voice of the requested gender), which is why the accent was removed rather than kept with a fallback.

## Field crash triage (owner: "installed but won't launch")
When the owner reports a launch crash on their phone, run the ladder in order — prove the artifact, then the state, then stop and ask; never touch code or re-send anything on a hunch: (1) sha256 the delivered APK against the build output (did they get the bytes you built?); (2) install the exact delivered bytes on the emulator and prove a resumed activity AND rendered pixels (crash buffer + uiautomator + PIL palette scan; resumed-but-blank = failure); (3) reproduce the owner's exact transition — build the PREVIOUS version in a git worktree, seed their saved prefs, then upgrade-install the new version (`install -r` keeps state, like their phone); (4) diff the APK file listing + dex class lists old-vs-new (R8 shrink is monotone — a strict superset is structurally sound; the dexdump colon-format trap is in the `android-compose-debug` gotchas ref); (5) if every check is clean, the crash is device-specific (stock AOSP emulator does not catch OEM/Android-version bugs — the owner's phone is a Samsung): do **NOT** re-ship the same bytes as a "fix" — ask for the real stack trace (crash dialog "More info" / long-press OK, or `adb logcat -d | grep -A 40 FATAL`) and fix the exact cause. Full commands + prefs-state recipes: `references/field-crash-triage.md`.

## Pitfalls
- **The AVD directory and the AVD name disagree.** `~/.android/avd/` holds `S24Ultra.avd` but the config is `S24Ultra_API_36.1.ini` — `emulator -avd S24Ultra` exits instantly with "Unknown AVD name"; the launchable name is **`S24Ultra_API_36.1`** (the .ini stem, not the .avd dir). If a launch prints that error, run `emulator -list-avds` instead of guessing.
- **Build the right project.** Since the promotion, the journey app IS the root build (`settings.gradle.kts` includes only `:app`); the leftover `ux-redesign/` dir is an empty shell — never expect a build there. `./gradlew` at the root is correct. (Pre-promotion history: ux-redesign was a separate build; old notes saying "cd ux-redesign" are stale.)
- **Repo-wide cleanup = file-level plan, then approval gate.** For any deletion/reorganization pass (retiring the old root tree, promoting ux-redesign to root, pruning planning-era docs), first produce an explicit DELETE / REORGANIZE (git mv) / MODIFY / KEEP list covering every tracked file, then stop and wait for the owner's explicit approval before touching the tree. Status: a full cleanup plan was presented 2026-10-21 and is **pending approval** — re-confirm with the owner before executing deletions.
- **Never drive completion from a theme palette role (primary/tertiary).** Early versions tinted completion with gold (tertiary) and the owner rejected it; a later 4-hue per-lesson cycle was also rejected. All state cues — map nodes, path line, celebration card, in-lesson stars, ScoreRing — take their colour from the fixed `success` / `incomplete` semantic tokens so state stays consistent across all 5 themes.
- **Docs and code move together** — a code-only change to node states/themes leaves `ux_design/v3-journey.md` lying to the next session.
- **Keep the tappable frontier.** Any simplification of node states must leave exactly one incomplete lesson tappable; a map that is all-locked is a dead app.
- **The path is a thin LINE, not a road (v3.3 contract).** The owner rejected both the 8dp connector look (read as "horizontal lines") and the 64dp 3D tube ("too thick, should be a line"). Current: one ~8dp route line (`PATH_WIDTH_DP` token) with the full S-curve meander, coloured per the two-state contract. Lesson names are NOT drawn on the map — tapping any node opens a short rectangular popup (name + concept progress + START/CONTINUE/REVIEW chip; locked shows a note; tap outside dismisses).
- **Each visual instruction from the owner REPLACES the contract.** This map went connector → ribbon → tube → line across a few turns, and colours went 4-hue cycle → two-state; the owner iterates by screenshot with terse directives. When they react to a shipped design, rewrite the design tokens + the matching `v3-journey.md` section in one pass — don't layer a third variant on top. They explicitly want such changes made **in the design tokens** (JourneyScreen.kt constants + Color.kt semantic roles).
- **Every shipped build gets an identity.** Bump `versionCode`/`versionName` in `app/build.gradle.kts` (the app is the repo root) and update the hardcoded version-marker string in the JourneyScreen header in the same commit — the marker is a literal in code and has drifted before (a v3.7 marker on a v3.8 build); all three move together on every shipped build. When the owner reports "wrong APK" / "it still looks the same", first establish which build their phone actually runs (marker / Settings → About) — a stale install was the root cause of repeated "horizontal lines" complaints; a fresh install replaces it.
- **Seeding test state: use the prefs file format Android actually writes.** Hand-injecting `shared_prefs/aws_trainer.xml` for fast emulator tests (37-of-38 style): API 36 silently discards a file whose set is written `<string-set><item>` — the app boots to an empty state with NO log error. Write it exactly as Android does: `<set name="completed_concepts"><string>id</string>…</set>` (plus `<string>`/`<boolean>` keys; see the file Android writes after one real quiz). Pipe it in with `adb shell "run-as <pkg> sh -c 'cat > shared_prefs/aws_trainer.xml'" < file` — run-as can't read /sdcard, so `cp` from /sdcard fails. Concept ids extract from `demo/Content.kt` (exclude the 8 lesson ids).
- **android.graphics colour literals are Long in Kotlin.** `p.color = 0xFF0B1F3A` is a Long (value > Int.MAX) and fails to compile against `Int` fields — define named `private val X = 0x....toInt()` constants. Same for `intArrayOf(...)` gradient stops.
- **Verify map changes with pixels, not just the build.** Headless emulator + `adb exec-out screencap` + a PIL row/column scan. Caveat: a diagonal stroke measures much wider in a horizontal row-scan than its token width (an 8dp line reads 13-17dp at 40-53 degrees) — compare against the vertical stub or measure perpendicular before declaring a density/scale bug.
- **A wrapping Row that contains a weighted child eats the whole row.** The v3.23 settings phantom gap: the speed row wrapped Slider + value text in a nested wrapping Row whose Slider had `weight(1f)` — a wrapping row with a weighted child measures at the full available width, so it consumed the row and starved the adjacent `weight(1f)` title column to zero width; the title then wrapped one character per line into a ~500dp invisible gap (a one-character sliver, top-left, is the only visual trace). Keep `weight` on children of the FLAT outer row, give sliders an explicit height, and verify such layouts with `onSizeChanged` logs — a screenshot shows only the symptom (white space), not the 0-width column.
- **Drive the welcome flow step-by-step, not blind-chained taps.** tap -> uiautomator dump -> assert state -> next; chained blind taps fail about 1 in 3 on the emulator (keyboard / date-picker timing). A Samsung-IME handwriting dialog can open after `input text` — dismiss with keyevent 4 / BACK, re-dump, then continue. When taps stop registering at all (AVD input-pipeline state — taps silently re-type text, buttons never fire), stop fighting the UI: verify the behaviour through the in-app self-test hooks + uiautomator dumps instead of shipping an unverified UI path.
- **New visual elements are auditioned, not shipped.** Any NEW element the owner frames as a design choice (success tones, logo, certificate, navigation patterns) gets 2-3 concrete rendered options (tones: `references/sounds.md` recipe; logos/certificates/diagrams: generated SVG/HTML mockups — the `theloop` skill for logos), the owner picks, and only the pick is implemented. Never ship one unreviewed design; after a pick, implement exactly it — do not re-generate. If the vision-analysis provider is down, verify the rendered mockups by DOM bounding-box checks (browser js) + a PIL palette-colour-fraction scan of the expected regions — never send pixels you have not verified one way or the other. - **A changed default never reaches an existing install.** `AppState` persists every key on every mutation, so a device that has ever run the app carries a saved value that beats the code default on next load — shipping "default speed 0.8×" leaves a field phone at its old 1.0×. When the owner asks to change a reader default: first check the current code (v3.23.1 already set Male/India — two of the three asks were verified no-ops, not omissions), change BOTH the in-memory initialiser and the fresh-install prefs read in `state/AppState.kt`, and tell the owner explicitly that their phone keeps its saved value (clear app data, or move the control, to see the new default).
